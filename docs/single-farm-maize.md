# 作物重构与单农场玉米场景

本页说明 2026-10-24 的代码边界、执行过程、兼容策略和验证方法。玉米参考场景仍是 `scenario_single_farm_maize_full_season`；没有增加水稻或新的四组经营场景。

## 完整场景与运行入口

[scenario_single_farm_maize_full_season.py](../fairy/scenarios/maize/scenario_single_farm_maize_full_season.py) 是完整、独立的场景文件。其中包含田块尺寸、作物与品种、初始土壤与库存、真实设备配置、任务说明、`build_events_flow()`、完整 workflow、公开工具 Oracle 和 `validate()`。它不导入其他场景的私有经营流程。

```bash
PYTHONHASHSEED=0 python3 -m fairy.cli \
  -s scenario_single_farm_maize_full_season \
  --build-oracle --run-oracle-tools --replay --evaluate \
  --output-dir /tmp/fairy-single-maize
```

命令先执行公开经营工具、保存工作流，再从新初态回放、评价。单独 `--build-oracle` 只构建参考，不执行经营工具。本轮验证没有调用服务器模型；真实 LLM 自主运行需使用项目已有 agent/provider/model 配置。

## 模块边界与修改原因

| 代码 | 现在负责什么 | 为什么这样改 |
| --- | --- | --- |
| `crops/catalog.py` | 作物身份、品种和类型明确的农艺规则注册 | 删除平铺的重复常量；声明需求，不声明设备或仓库拥有什么 |
| `crops/rules.py` | `ScalarRange`、`PlantingRules`、`HarvestRules` | 温度、深度、水分的包含/不包含边界能执行检查，也能生成准确说明 |
| `crops/runtime.py` | `PlantingEvent`、`ReplantPlan`、`CropStatus`、观测特征 | 作业传递明确事件；区分当前活植株与历史成苗记录 |
| `crops/maize.py` | 独立玉米生理、冠层、生物量、产量和自身日游标 | 不把玉米阶段塞进大豆枚举，也不读取 App 或推进其他环境引擎 |
| `crops/soybean.py` | 原有大豆三类生理引擎及其状态序列化 | 保留原模型系数，形成明确的大豆模型边界 |
| `crop_dynamics.py` | 共同接口、模型工厂和显式注册 | 只有构造入口选择具体实现，公共 App 不按物种分派 |
| `soybean_dynamics.py` / `maize_dynamics.py` | 本作物与环境之间的输入转换、生命周期和公开投影 | 生理差异留在对应适配器，不把土壤、水肥、病虫的整轮日推再复制一份 |
| `physics_orchestrator.py` | 时间日界、队列提交、公共环境与作物的执行顺序 | 移除 `physics.maize` 分派，所有作物走同一套公共编排 |
| `farm_physics_state.py` | 每个农场独立的环境与 `crop` 状态容器 | 删除特定作物的可空专属槽位；旧三个引擎访问名仅作为兼容别名 |
| `field_geometry.py` | 种植面积、边界宽度、种子数量 | 同一几何用于种子、时长和粮重，区分种植宽度与未种植边缘 |
| `equipment.py` | 设备实际拥有的机具和作业覆盖上限 | 种植玉米不再凭空增加设备能力，reset 也不丢失设备配置 |
| `operation_plans.py` / `tractor_operations.py` | 作业预检、耗时、车载物料、作物事件提交和账目 | 先验证完整计划，再开工；设备不再直接操作大豆阶段枚举或玉米内部组件 |
| `tractor_tool_contracts.py` / `tool_contracts.py` | 从实际设备、田块及同一农艺规则构建工具契约 | 删除 App 内按物种拼接、事后覆盖工具描述的代码 |
| `tractor_app.py` / `shared_tractor_app.py` | 单场绑定或显式解析 `farm_id`，调用相同作业 | 保留真实 Python 参数；共享设备不会记忆一个隐式“当前农场” |
| Robot / Drone / Sensor | 观测产品、实际覆盖、噪声和设备资源 | 用 `CropStatus` 判断当前是否存在作物；收割后不能继续报告满苗和活冠层 |
| `farm_environment.py` | 共同模拟时钟、区域天气和所有农场同步 | 时间绑定不再取决于作物名称；空闲农场也同步到同一时刻 |
| `crop_snapshot.py` | 公共环境、模型、队列、日期、参数和随机流快照 | 快照格式不再属于玉米；每个生理模型序列化自己的状态 |
| `farm_checkpoint_state.py` | 历史检查点迁移和新完整检查点入口 | 旧格式先加载田块再恢复 profile 与 RNG；新格式直接使用保存的完整模型，避免天气生成器丢失或定制天气被全局模板覆盖 |
| `legacy_calendar.py` | 历史无物理大豆场景的日期与压力代理 | 把兼容行为命名并隔离，不能误当成所有作物通用模型 |
| `tool_utils.py` / `type_utils.py` | 真实签名、参数类型、有限值与契约检查 | 运行参数检查不再取决于文档是否启用严格审查 |
| `agents/agent/agent.py` | 把类型化参数拒绝记录为工具错误和可恢复观察 | 拒绝不能被日志记为成功；这里没有新增农艺判断 |

## 一次动作如何生效

普通播种读取目标田块的播种规则、实际设备和真实几何，检查整地完成情况、种子类型、机具、播深、株距、目标区块平均土温/墒情与场景窗口。它计算不可变的 `PlantingPlan`，包括种子量、耗时和完成日期，并向权威作物模型进行无副作用预检。

可预见的拒绝不扣种子、不耗油、不推进时间，也不偷偷安装物理状态。成功作业推进唯一时钟，提交作物事件、管理输入及资源账，记录实际播种元数据。公开 `planted`、阶段和当前苗情由作物模型投影，设备不再自行拼另一份生长状态。

普通起垄在田内仍有作物时拒绝；起垄不是一个隐含的毁苗工具。重播是另一种明确动作：全量重播重置目标垄的作物周期，局部补苗保留已建立的物候。其支持模式由作物声明，并由模型实际实现。

大豆旧补播与首次播种的限制不同，因此 `replanting_rules` 单独声明历史行为。玉米默认继承首次播种规则；已出苗玉米尚不支持局部补苗，必须明确选择全垄重播。不能因为实现统一接口，就给旧操作偷偷增加原本没有的门槛。

补播响应继续返回 `stand_fraction_before`、`stand_fraction_after` 和 `phenology_reset_ridges`；设备保存日志保留原有字段名称和三位小数口径。成苗变化来自同一个 `ReplantPlan`，Agent 可以直接判断动作效果，设备不会另算一份苗情。

每天只有公共编排器推进土壤、管理和病虫。作物在病虫更新前后有明确的两个阶段，以保留两个原模型各自的日内输入口径。相同时间戳只提交待处理动作；不重复演化一天，也不因收割再干燥一天。

当前植株存在与历史成苗率分开：收割后公开苗情、机器人出苗检查和冠层观测均为空地语义。玉米相对产量采用生物干物质同口径归一化；粮箱容量按标准含水率质量计算，两者不混用。

## Agent 获取什么工具信息

`FarmWorldApp.get_crop_capabilities()` 对所有作物公开身份、几何、播种、补播、收获和储存规则。参数范围、种子例外及机具要求来自同一份类型化规则。

`get_tools()` 保持真实函数签名。共享工具的目标依赖 `farm_id`；静态 schema 可以展示多个田块的范围包络，实际调用必须按所选田块精确检查，不能把并集当成每个农场都合法。物料装载属于实际仓库；种子是否适合目标田块在田间动作中再次检查。

例如旧大豆 `EARLY_COLD` 的最低土温为包含边界的 8°C，其余种子为严格大于 10°C。这些差异同时出现在规则检查和工具说明中。没有在 App 中另外硬写一份大豆或玉米文案。

机器人一次任务最多覆盖 8 垄，物理观测模型每批最多 4 垄。工具会实际分批生成每一垄的观测产品，再汇总覆盖、时间和电耗；超过任务上限才报告未覆盖。不能把一次仅生成 4 垄产品的调用描述成已经检查 8 垄。

## 历史场景兼容与快照

不传 `crop_id` 的 `FarmWorldApp()` 保留历史大豆日历兼容入口、库存默认值以及 71 m 作业边界。显式 `crop_id` 选择物理模型；大豆、玉米都可以使用实际长度、垄距和行数。当前固定探头布局仍限制为 64 垄，尚未泛化传感器布局。

旧场景还使用裸地的 `stand_fraction` 表达初始成苗条件，例如压实地块的 0.84。这种历史初始化语义在兼容适配器中读取，不能在播种时一律覆盖为 1，也不能把裸地当前活苗数为零当成新种子的成苗条件。

新显式作物的库存起始为空，场景必须配置物料。默认旧设备保持原五种机具和历史内置起垄能力；需要挂载特定起垄机的设备显式设置 `ridging_implement`。这些都是设备配置，不由作物身份制造。

农场快照统一包含 `crop_configuration`、`physics_state`、`weather_state`，配置版本为 2。物理快照包含各模型参数、环境、日期游标、待处理动作及随机流。恢复时先解析到独立对象并检查身份/几何/时区，再安装，错误快照不能只替换一半。生长期的显式物理农场不能缺少物理快照。旧无作物身份的浅快照只在历史兼容入口接受，不能借此跨作物恢复。

恢复续跑需要调用者先恢复共同模拟时钟，再加载农场和各设备快照；共同仓库单独保存和恢复。农场 reset 清空本场作物与待处理动作，不清空共享仓库。固定随机种子验证使用 `PYTHONHASHSEED=0`。

旧单场的北京时间/UTC日界混用继续按用户要求保留为 [TIME-001](known-issues.md)；本玉米场景显式统一为北京时间。本次没有修改 TimeManager 的实现。

## 验证与实际限制

验证不能只看固定 Oracle 跑通或最终 validator 的布尔值。回归同时比较真实工具错误、partial、收获垄数、仓库粮食、物料和时间。处理中发现过“测试全过、最终验证通过、实际没有收获”的回归，已保留中间证据，不能把这种版本作为完成结果。

重构前完整当前代码冻结在 `/tmp/fairy-crop-refactor-start-20261024`，包含已有共享仓库改动。基线为 393 项测试；315 场景中 286 完成，29 发生原有异常。29 项为 18 个缺少外部 Excel 文件、11 个物理时间倒退；没有把异常写成正常通过。

最终结果以 [独立冻结验证报告](../validation_runs/crop_runtime_refactor_20261024/final/REPORT.md) 及同目录的测试日志、逐场对照为准。`validation_runs/` 按仓库规则忽略；中间版本另行归档，不能与最终稳定版本混用。

最终冻结候选的全套测试为 **456 passed**。315 个场景对照仍为 286 完成、29 个同原型既有异常；没有新增工具错误或减少收获垄数，所有场景的实际调用时间轴一致。玉米的真实 CLI 执行、保存后新初态回放和评价成功：136 步、64 垄、10,700.76 kg。

有一项明确的模型数值更正：`scenario_full_season_heinong84_edge_low_fertility` 的 0–3 垄进行了 `full_replant=True`。旧版虽然重置物候，却保留被终止作物的冠层和生物量；新版完整清除并按未出苗地表计算土壤。该区出苗推迟一天，全场入库从 8,216.22 kg 变为 8,205.06 kg，减少 11.16 kg（约 0.136%）。其他 60 垄逐笔收获质量相同，全部 64 垄、工具错误数和时间均相同。这是已记录的生命周期纠错，不能描述成所有场景产量逐位不变。

新增测试包括：第三虚构作物的契约扩展、同规则元数据/执行边界、现存作物起垄零消耗拒绝、重复播种、快照无效数据原子拒绝、缺物料不创建物理状态、收后空地观测、第二季种植、参数错误的真实 Agent 请求/恢复链、JSON 快照续跑以及原全季和回放。

玉米是简化模拟模型，只有一个虚构品种。它使用原生玉米阶段、温度积累、光截获和水肥/病虫胁迫，R6 后进入干燥和田间损失。它没有经过独立田间数据校准，不宣称现实产量预测、最高产 Oracle、真实氮磷钾平衡或已实现水稻。

既有通用施药剂量、全田水肥接口缺少作业耗时、逻辑干燥缺少真实耗时/能耗等问题没有随本轮一并解决。当前结构允许注册其他作物的定义和真实模型；水稻的插秧、淹水、排水等新过程需要明确新增物理过程和作业能力，不能只增加名字或几个配置开关。

扩展时使用 `register_crop_definition()` 注册农艺需求，使用 `register_crop_dynamics()` 注册真正的生理实现及观测特征，再在完整场景中配置田块、设备和物料。复用现有播种、补播和收割作业不需要修改公共 App；新增农业过程仍需实现对应模型和作业能力。测试中的第三虚构作物只验证工具契约扩展，不冒充已经实现第三种作物物理。
