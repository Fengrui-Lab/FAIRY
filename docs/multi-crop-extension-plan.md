# 玉米、水稻扩展：当前代码审查与设计建议

审查日期：2026-10-24。下文“当前代码”描述的是原始审查基线 `6a8f8bb`。后续按用户指令先实现了单农场玉米，见 [已实现的范围、场景与兼容证据](single-farm-maize.md)。水稻和多农场玉米仍为后续方案。

2026-10-25 更新：大豆生长增量未传入养分结算的数据流已修复，具体范围、研究依据和仍未实现的农学过程见本文末尾 [生长耗养修复与农学边界](#2026-10-25-生长耗养修复与农学边界)。下文保留原审查语境，历史测试数和当时的实施状态不作为本次修复的验证结果。

仓库归属现已更正，见 [共有仓库设计](shared-warehouse.md)。下文保留 `source_farm_id` 的建议已作废：种肥药油来自同一仓库，机上物资可跨场使用；粮箱来源及仓库粮批用于追溯。

## 结论与范围

当前代码已经有多农场的状态隔离、固定设施归属、共享移动设备及公共时钟，但作物链条仍是大豆模型。`HEINONG84`、`HEINONG58` 等是大豆的品种，不能通过给 `SeedType` 增加 `MAIZE`、`RICE` 就得到玉米、水稻支持。

建议先实现“大豆农场 A + 玉米农场 B”的全季场景，再增加具有独立水层管理的稻田。第一阶段每场只种一种作物，不同时扩展轮作、间作、跨地区天气和完整渠道水网。身份与序列化结构应能区分田块与种植季，避免以后把作物永久写死在农场对象上。

共享是设备资源归属，不代表每台设备天然可以操作所有作物。拖拉机的油箱可以共用；播种机、收割割台、田间通行规则和水稻移栽设备必须有自己的适用范围。

| `fairy/physics/observation_model.py` | 通用噪声观测骨架，但参数、地面检测与传感器类型仍有限 | 可以复用观测过程；作物参数、可见产品和稻田水位观测需要配置 |
| `fairy/apps/farm_world/drone_operations.py` / `robot_operations.py` | 旧观测代理按大豆阶段生成；机器人诊断有固定 `aphid` / `leaf_spot` 标签 | 观测与诊断需读取作物参数；不能把一般压力检测包装成准确的其他作物病虫种类识别 |
| `fairy/apps/farm_world/tractor_operations.py` | 固定几何计算种子数；统一机具、播种门槛；收获要求 R8 且含水率不高于 18% | 当前规则会错误拒绝或接受新作物作业 |
| `fairy/apps/farm_world/irrigation_app.py` | VWC 达到 0.30 就拒绝灌溉，按运行小时注水 | 不适合维持、降低或排空稻田水层 |
| `fairy/apps/farm_world/shared_tractor_app.py` | 载荷和粮箱有农场来源，尚无通用作物批次身份 | 同一来源农场也可能在不同种植季产生不同产品；不能只靠来源农场防混装 |
| `fairy/physics/profiles.py` | 当前 profile 主要捆绑哈尔滨天气与大豆场景事件 | 地区天气、作物模型和场景冲击应该分别选择，避免“改 profile 名称即支持作物” |
| `fairy/controllers/agent_config.py` | 现有农场提示词仍有 `soybean farms` | 通用提示词需要作物中立，实际作物信息由场景和能力目录提供 |

`configure_physics_profile(**scenario_metadata)` 可以接收附加标签，但写入一个 `crop="maize"` 标签不会选择玉米物理模型。未知种子回退是物理桥接和接入新作物时的风险；当前公开播种工具仍约束现有大豆 `SeedType`，并不表示它已经接受任意玉米/水稻种子。

当前生产模型本身是简化模型。例如冠层代码明确没有完整模拟氮固定、器官碳分配和籽粒数量；不能把现有大豆路径当成已校准的完整生理模型，再简单复制参数给玉米。

## 四层边界

| 层 | 负责 | 多作物扩展的边界 |
| --- | --- | --- |
| Agent / Engine | 模型调用、工具调用与日志、事件执行、时钟协调、保存回放 | 消费场景给出的工具与状态；不写“大豆到 R8 才能收获”等规则 |
| 农场物理 | 土壤、作物生长、病虫与管理效果、成熟和产量演变 | 依据作物模型及动作输入演化真实状态；不负责 LLM 提示词和机具库存 |
| App / Operations | 设备能力、农场定位、作业前置条件、物料与耗时、观测、提交动作 | 用目标作物规则检查作业，把动作交给物理；不直接把作物阶段或产量改为期望答案 |
| 场景文件 | 农场和地块几何、物种与品种、初态、设施设备、天气、任务、完整 Oracle、验收 | 每个场景完整可读；只实例化模型和参数，不在场景中临时重写物理算法 |

`FarmEnvironment` 继续负责农场目录、共同时间与同步；`FarmContext` 继续绑定一个农场的 world 和固定设施。无需为每个物种复制一套 Agent、Engine、共享拖拉机或时钟。

## 身份、地块、阶段与参数

建议增加以下概念，具体名字可在实施时调整：

- `crop_id`：物种，例如 `soybean`、`maize`、`rice`。
- `cultivar_id`：该物种下的品种，必须在对应作物目录中存在。
- `crop_cycle_id`：本次种植季身份，连接播种、作业、收获与粮食批次。
- `management_unit_id`：最小管理单元。旱田可以是垄或垄组，稻田可以是有边界的水田小区。
- `FieldGeometry`：面积、长度、单元间距、种植行数、作业覆盖与地图位置。面积从几何求得，种子数从实际覆盖、行距/株距求得。
- `StageState`：保存 `crop_id`、物种原生阶段、发育进度，以及出苗、开花、成熟等明确里程碑。下游按所需里程碑或作物策略判断，不把玉米/水稻的阶段强塞进大豆枚举。

第一版可以保留现有 `ridge_id` 工具入口以兼容大豆；新布局层应提供清晰的单元映射。水稻入口应明确称水田小区，不向 Agent 伪称稻田存在同样的 64 垄。第一版也不必立即支持任意形状多边形或一场混种。

品种参数与模型逻辑分开：品种文件负责积温、密度响应、耐性等有来源的参数；作物模型负责转段、胁迫响应、成熟与收获规则。地区气候和情景冲击不放进品种定义。

## 物理模型怎么拆

建议由一个明确的作物目录构建作物模型组合：生育、冠层/生物量、管理响应、病虫响应、收获。先把当前大豆行为封装为 `soybean` 实现并验证，再加入 `maize` 与 `rice`。不需要马上把每个小函数都做成插件。

公共物理编排器保留一次动作提交和每日推进顺序，输入输出使用共同的明确结构。作物特有阶段转换和生理参数移到作物实现；土壤、天气、随机种子与时间协调继续复用。快照需要记录所选模型和版本。

特别要处理 `physics_orchestrator.py` 的 `_compute_water_stress()`：其水分胁迫曲线当前直接写在编排器中，单改土壤参数不能让胁迫响应自动适配新作物。需要把根区状态与相应作物/土壤参数一起送入明确的胁迫策略。

同文件 `_compute_biotic_stress()` 的病虫草压力权重也直接写在编排器中，应随作物响应策略明确配置，不能把现有固定权重默认解释为所有作物共同的生物规律。

| 子系统 | 玉米需要增加 | 水稻需要增加 |
| --- | --- | --- |
| 建植与生育 | 玉米阶段与品种转段参数；适用播种深度、密度、土温条件 | 明确第一版采用直播还是移栽；对应的建植、分蘖、生殖与成熟阶段；若移栽，增加苗龄/移栽恢复状态 |
| 冠层与籽粒 | 玉米冠层、密度、开花与籽粒形成/灌浆响应 | 水稻冠层、分蘖或其明确简化表示、穗与籽粒形成/灌浆响应 |
| 水肥 | 旱田土壤骨架可复用；需有对应根区用水、胁迫与肥料响应 | 田面水层、入渗/渗漏、排水/溢流、水源交付与作物水分响应；肥料在淹水条件下的响应需明确定义简化范围 |
| 病虫与处理 | 对应作物的病虫敏感阶段、剂量响应和产品限制 | 对应作物的病虫敏感阶段、剂量响应和产品限制 |
| 收获 | 玉米成熟和收获门槛、适配割台、田间损失与产品水分 | 稻谷成熟、田面排水和设备通行、适配收割设备、损失与产品水分 |
| 收储 | 玉米批次、安全储存与干燥规则 | 稻谷批次、安全储存与干燥规则；若无加工模型，不把稻谷当成大米 |

这里的稻田模型针对具有水层管理的水稻场景，不假定所有水稻都持续淹水；直播/移栽与淹水/干湿交替等水分制度需要分别配置。稻田水分必须守恒。田面蓄水变化至少要由降雨、实际灌水、入渗、蒸发、排水和溢流共同结算；根区模块接收相应通量，不能让同一份水既增加田面水层，又被根区再次凭空添加。`water_depth_mm` 不能与 `root_vwc` 共用一个字段。

现有编排器还有独立的 `_apply_subdaily_irrigation()`。稻田通量必须同时接入日内动作生效和每日推进，并共享水量账与结算边界；只修改每日 `soil.update_day()` 会遗漏当天工具提交的水。

当前 `nutrient_index` 可以保留为声明过范围的简化代理；如果产品要表达氮磷钾库存、吸收和肥效，就应另加可守恒的养分状态，不能仅换字段名称就声称实现养分平衡。

原始审查基线的另一个集成限制是：`management_effect_engine.py` 有按 `daily_biomass_g_m2` 计算吸收的项，但 `physics_orchestrator.py` 的 `_build_management_crop_inputs()` 始终传入 `0.0`，因此当时尚未使用实际生物量驱动养分消耗。2026-10-25 已修复这条数据流，改为用本日实际生物量增量完成一次耗养结算，见 [更新说明](#2026-10-25-生长耗养修复与农学边界)。这项修复仍不等于完整的作物吸肥或氮循环模型；公开营养字段同步与真实养分过程应分别说明。

## 工具、设备与 Agent 信息

现有设备归属方案保留：每场固定传感器、灌溉设施独立；共享设备拥有唯一的电量、燃料、挂具和载荷。新增设备按实际资产实例创建，例如移栽机需要独立状态；不能让普通拖拉机凭空拥有移栽能力。

建议分两层提供能力信息：

1. 静态 Schema 反映真实 Python 签名、参数类型和真实设备所拥有的动作。没有安装水位探头就不提供可用水位读数，没有相应能力就不注册该动作。
2. 增加按目标农场查询的能力工具，返回该场物种/品种、几何与单元 ID、可用建植方式、允许机具、当前作业门槛、观测能力、限制及单位。Schema 负责能否调用，目标能力与运行时校验负责当前能否完成。

同一个共享拖拉机服务大豆和玉米时，`cultivar_id` 的合法值依赖 `farm_id`/目标物种；不能仅发布一个场景全局品种枚举，就认定每个品种都适用于每场。可以在 Schema 中列设备支持的集合，再在能力工具与执行前检查目标依赖关系；也可以使用明确的作物专用建植动作。最终要选一种完整实现，避免描述与实际检查分别维护。

具体接口调整包括：

- 播种：按目标作物检查种子批次、机具、播深、行株距/密度、真实面积和库存；未知物种/品种拒绝，不能静默回退大豆。
- 移栽：如果第一版水稻采用移栽，单独实现苗批次、设备能力、覆盖、株行距、苗龄及耗时；如果采用直播，场景与工具明确说明未模拟育秧移栽。
- 灌排：旱田保留相应灌溉动作；稻田增加真实支持的注水/排水控制和田面水位读取，检查交付水量、流量/耗时和额度。只写目标水深不能保证瞬间到达。
- 收获：从目标作物规则读取成熟、湿度和通行条件，检查适用机具及粮箱产品身份。
- 观测：保留真实覆盖与观测噪声；稻田水位来自对应设施，作物阶段和健康结果包含物种与观测时间。公共观察不能凭空变成所有内部物理真值。
- 日志：写入 `farm_id`、管理单元、`crop_id`、`cultivar_id`、种植季、资源、开始/结束/生效时间，保证操作、回放与结果可以对应。

文案、能力查询和运行时检查应读取同一份规则数据；Agent 引擎不维护第二份作物门槛表。测试必须检查实际发给模型的工具 JSON，并用同一输入实际调用接口，防止只验证工具名称存在。

## 种子、粮食与快照

现有 `source_farm_id` 和 `grain_origin_farm_id` 继续保留，再扩展载荷身份。种子需要物种、品种与数量单位；粮食批次需要来源场/单元、种植季、产品、质量、含水率和质量口径。

第一版可以明确禁止跨物种混箱，要求卸空后换作物；同一农场的不同产品也应检查。仓库按产品/批次记录，汇总展示不能把大豆、玉米和稻谷的总 kg 当成可以互换的单一库存。若要比较不同作物经营收益，需要真实配置的价格与成本口径，不能把合计 kg 当成利润。

现有 `kg` 已含收获模型的市场等价折算，实施时必须明确保留还是迁移为湿重、干物质量、标准水分重量，并分别命名。不能仅在干燥动作再扣一次水分重量，造成重复折算。

保存/加载应增加 schema 版本、作物模型标识、种植季和批次身份。旧快照只在明确的兼容适配中解释为大豆；明确指定了未知作物的新快照必须拒绝。加载前检查跨场、跨作物配置是否兼容，不能改一半后才报错。

## 场景怎么写

建议未来新增独立场景文件，每份都含完整配置、初始化、任务说明、`build_events_flow()`、Oracle 和验证，避免从另一份场景借用私有参考流程：

- 大豆 + 玉米双场全季：验证同一季不同生育窗口、设备排程、载荷切换与农场隔离。
- 玉米不同水分条件双场：验证根区管理与相应作物响应。
- 水稻单场全季：先验证田面水层、建植方式、排水收获与水量收支。
- 玉米 + 水稻双场全季：验证旱田与稻田并行演化、固定设施差异及共享设备的适用限制。

这是建议的后续场景顺序，本次尚未添加这四个场景，也没有把先前提出的场景数量自动视为本轮实现任务。

Oracle 应使用公开可见的观测和正常作业工具，写清季节节点、资源补给、复查和条件不满足时的处理。天气与初态可以由场景定义；中途不直接把水分、病虫或成熟状态重写成预期结果。内部真值可供离线审计与验收，但要与 Agent 实际观测分开记录。

## 实施顺序与验收

1. **固化大豆基线**：区分测试通过、Oracle 工具成功和模型可信。记录模型版本、参数、随机种子、工具描述与回放结果。
2. **抽出作物身份与大豆适配**：去掉未知种子回退和跨引擎大豆枚举转换；先验证既有大豆行为、工具签名与回放兼容。
3. **参数化几何、设备能力和批次**：种子数、面积、作物适用性与来源账一致；增加目标能力查询，验证模型看到的真实 JSON。
4. **实现玉米并跑双场全季**：独立生育/成熟规则、观测、资源与收储完整闭环。原大豆场不能因另一场新增模型而变成玉米规则。
5. **实现稻田水量与选定建植方式**：先单场验证水量收支、真实作业时间、传感器和排水收获，再组合多场。
6. **跨作物验收**：覆盖错误品种/机具被拒、禁止混箱、设施隔离、同一共享设备连续耗能、非作业场仍随时间生长、跨日动作只结算一次、保存后新实例回放一致。

产量验证必须有参数来源与独立合理性检查；能从播种运行到入库不代表已经有可信的现实产量预测。若仍使用简化模型，应在能力与实验报告中明确精度边界。

旧单场日历问题按用户指令暂缓，见 [TIME-001](known-issues.md)。新作物场景应显式配置业务时区，不能继承旧单场 UTC 回退。

## 2026-10-25 生长耗养修复与农学边界

本轮修复大豆生长与管理引擎之间的数据缺口：冠层引擎已经计算并累积生物量，但大豆适配层一直把 `daily_biomass_g_m2=0.0` 交给管理引擎，导致生长相关的营养指数扣减为零。该值表示每垄当天每平方米新增的地上生物量，单位为 `g/m²`，不表示累计生物量，也不表示吸收的氮公斤数。

### 本次实现的结算边界

日初先处理背景衰减和当日管理动作。大豆在冠层初始化之后记录生长前的地上生物量，完成当日生长更新后，以前后差值得到实际新增量，再交回物理编排器。初始化时建立的初始冠层质量不算作当天通过生长新增的质量。

管理引擎用本日实际新增量完成一次生长耗养结算，并记录本日生物量增量与对应的营养指数扣减。日初的 `None` 表示等待实际生长结果；实际增长为零的 `0.0` 表示已知当天没有生长，二者不能混用。同一日期的查询、施肥、收割或其他工具调用不能再次扣除该日的生长耗养。保存与恢复需要保留这项结算状态，不能从累计生物量重新推算并重复扣账。

上述当天生长后结算针对大豆。玉米继续在日初提交上一轮生长增量，保留原有计算顺序和数值；新增审计日期表示结算日期，不能据此把玉米的上一日生长说成当天发生。新增作物必须在日初显式提交数值，或以 `None` 延后并在生长后返回各垄增量，两处同时不提交仍会遗漏耗养。

本次沿用现有代理公式：

```text
生长耗养指数 = 0.00018 × 本日实际新增地上生物量（g/m²）
```

`0.00018`、每天 `0.0008` 的背景衰减及原有施肥响应曲线均未为拉大产量差异而调参。上述扣减仍是继承的综合营养指数净消耗代理；系数没有经过当地品种与土壤的田间标定，不能解释为作物全量氮吸收，也不能换名后当作 `kg N/ha`。本次没有新增假定的固氮补偿量、矿化补偿量或肥料氮含量。

### 尚未实现的过程与结果使用范围

当前仓库和设备记录的是肥料产品质量，没有完整的产品N-P₂O₅-K₂O成分、土壤矿质氮库、植株氮库、矿化、淋失、根瘤固氮和器官间氮再分配过程。本次修复因此只保证实际生长会进入既有耗养模型，不能声称已建立氮质量守恒或完整的N/P/K供需关系。

如果以后扩展真实氮账，需要明确肥料成分与施入面积，分别记录土壤供给、植株吸收和大气固氮等通量，并给阶段、根瘤和水分响应提供参数依据。固氮只能补氮，不能同时补偿磷钾；新增供给项也不能为了保持旧产量而任意抵消已修复的消耗。

修复会改变大豆全季营养轨迹及后续产量，需要重新运行旧场景、实际工具Oracle与回放，并对同一天气和相同作业时间下的管理对照重新计算。兼容性检查应说明场景能否继续执行、快照能否正确续跑和回放是否一致，不应要求继续复现“生长耗养为零”造成的旧数值。农学可信度还需要独立的土壤、品种和田间观测标定；不能仅以测试通过或模拟追肥增产证明。

### 下一阶段：先建立单场大豆氮供需闭环（设计，尚未实现）

用户要求参照实际情况后，修复漏接生长量只完成了数据流修正。以下问题仍阻止当前结果成为真实追肥效果解释：

1. `nutrient_stress_min=0.72` 使营养指数降到零时，营养生长乘子仍为 0.72。它是人为设定的缺肥响应下限，不是作物可用氮的质量约束，也不代表最终产量保底 72%。
2. 拖拉机用 `kg_per_ridge / 30.0` 换算肥效，没有除以实际垄面积。每垄施 2 kg，在 294.8 m² 上是约 67.84 kg 产品/ha，在 589.6 m² 上是约 33.92 kg 产品/ha，当前却得到相同指数增益。底肥和公开水肥接口也需统一单位契约。
3. 仓库没有肥料成分，土壤与作物没有独立氮收支，综合指数不能区分缺氮、缺磷钾或结瘤受限。
4. 拖拉机干撒追肥提交 `FERTIGATION` 时没有明确 `water_mm=0`，管理模块回退读取 `amount`，把归一化肥量当成水深。每垄施2kg就额外生成0.06667mm水，本场20垄约393.07L；目前追肥对照因此混入了水分输入差异。

面积换算与干肥携水属于应先修复的确定性单位/接口问题。响应下限则需随氮供需模型重做，不能只把0.72任意调小。当前目标区追肥前指数约0.667/0.724，高于0.35下限；这次约20kg增益主要来自既有曲线下局部营养乘子仅提升约0.011947、处理面积20/64垄且只影响施后生长，不能直接归因于下限。

下一步的范围先限定为单农场大豆、明确假定磷钾等其他矿质营养充足的氮供需模型；不把这个假定扩展到所有旧场景，不宣称已经支持完整N/P/K。真实大豆养分需求随生育和生物量积累变化，土壤供氮、根瘤固氮与后期组织再分配均参与供给，不能直接把全季需氮量当作施肥量。[Iowa State University，Nutrient requirements — soybean](https://crops.extension.iastate.edu/encyclopedia/nutrient-requirements-soybean)

单位首先统一为：`施入氮(kg N/ha) = 肥料产品质量(kg) × 产品氮质量分数 / 实际处理面积(ha)`。氮供需应在当天实际生长提交之前协调，不能先允许不受氮约束的生长，再只把负氮库截成零。固氮作为大气来源独立记账，并考虑所需碳成本；籽粒需氮与植株再分配不能遗漏。参数必须逐项记录来源、单位、适用条件和校准状态，不能把推广资料的地区建议量直接当作所有土壤的模型常数。

兼容策略是保留已有综合指数模式，让旧场景显式沿用或通过旧配置默认值恢复；新增氮供需场景必须提供完整配置，缺失成分不能静默猜成尿素，旧营养指数也不能直接换算成矿质氮含量。模型选择应在构建时完成，设备调用公共施肥事件接口。

完成这个阶段需要同时证明：

- 同施氮量/ha在不同地块面积上得到一致的单位面积输入；同总产品质量施入更大面积时剂量下降。
- 日氮账和全季氮账能够闭合，土壤吸收不超过可利用供给，未满足需求不会凭空产生氮。
- 在声明的试验条件下分别检查供氮充足、供氮受限、结瘤受限和缺水四组对照；供给充足允许不响应，水分限制不能由单独加氮直接消除。
- 输出逐日土壤供氮、固氮、植株吸收、氮缺口、实际生物量与籽粒形成，最终报告生物产量及入库产量。
- 同日操作、跨日、旧/新快照、单场和多场隔离、真实工具Oracle与回放均通过，再把该配置组合为双场任务。

本节是后续实现契约。本轮没有新增上述氮库、肥料产品体系或固氮模块；当前运行结果仍属于综合营养指数模式。
