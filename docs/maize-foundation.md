# 玉米场景：共享旱田工具与 WOFOST 8.1

玉米使用已有 `FarmWorldApp`、拖拉机、田间操作、观测和库存工具，
与大豆共用旱田 orchestrator 和 `WofostBackend`。没有独立的 MaizeWorld，
也不经由水稻的水田模型或 Oracle JSON 计划加载器。

## 场景与运行

玉米提供 **11 个 L1、4 个 L2、3 个 L3，共 18 个场景**。三个 L3 从裸地开始：

| 场景 ID | 任务 |
| --- | --- |
| `scenario_maize_l3_normal` | 完成正常条件下的整地、播种、水肥管理、收获、干燥和入库 |
| `scenario_maize_l3_water_limit` | 在有限水量下管理水分胁迫并完成收获入库 |
| `scenario_maize_l3_nitrogen_limit` | 在有限氮肥下管理营养胁迫并完成收获入库 |

安装项目的 WOFOST extra 后，可通过现有 CLI 运行，不需要 LLM：

```bash
uv run --extra wofost python -m fairy.cli \
  -s scenario_maize_l3_normal --build-oracle --replay --evaluate \
  --output-dir validation_runs/maize_normal
```

其余场景替换 `-s` 参数及输出目录即可。玉米场景自行选择 WOFOST；
不支持切换到旧的大豆生长模型。真实模型测试与 Oracle 软件验证分开报告。

## L1/L2 与来源季

L1 是条件已具备的单项农事任务，可包含挂具、装载及复核；L2 是观测、判断、
执行、等待和复查的短闭环；L3 负责完整种植季。共用基础任务只在正常来源季下
提供一套，水分和营养任务分别来自缺水与缺氮季，不为三个来源重复复制任务。

L1 ID 均为 `scenario_maize_l1_<task>`：

| 来源 | task | 目标 |
| --- | --- | --- |
| normal | `level`、`base_fertilize`、`form_ridges` | 分别完成整平、200 kg基肥、0.75 m起垄 |
| normal | `plant` | 使用已装载的 MAIZE_201，只播种0–3垄，4 cm播深、20 cm株距 |
| normal | `refuel` | 从真实来源检查点油量补满至100 L，核对仓库转移量；当前为51.63636→100 L，转移48.36364 L |
| normal | `harvest`、`unload` | 分别收获首个4垄批次、将其卸入接粮区 |
| normal | `dry`、`store` | 分别将全田湿粮烘干至14%、将已安全干燥粮食入库 |
| water_limit | `irrigate` | 全田30 mm灌溉，等待日步长响应并复查 |
| nitrogen_limit | `fertilize` | 全田80 kg肥料产品追肥，复查投入记录 |

L2 ID 均为 `scenario_maize_l2_<task>`：

| task | 来源 | 窗口和目标 |
| --- | --- | --- |
| `establishment` | normal | 裸地开始整地播种，播种后观察15天并复查全田出苗 |
| `irrigation_management` | water_limit | 第25天首次追肥之后、灌溉之前开始，管理15天；本窗口水量预算30 mm |
| `nutrition_management` | nitrogen_limit | 第25天首次追肥之前开始，管理25天；本窗口肥料预算80 kg |
| `harvest_storage` | normal | 第100天成熟但水分超限时开始，寻找可收窗口，完成全田收储闭环 |

日期编号沿用来源 Oracle 的管理窗口，不应解释为精确播后天数；整地、播种和
显式物理提交也会消耗时间。正常 L3 已从第145天改为第101天收获：第100天
观测日为2026-08-14，成熟日期为2026-08-13，籽粒水分约26.4%；再等一天水分
约24.6%，满足25%收获上限，但必须实际烘干到14%。缺水、缺氮来源仍在第145天
收获。此次不改变天气或原生作物参数。

子场景目录按 `l2_l1_splits/maize_<variant>/` 组织，每个任务有独立 Python 模块。
同目录的 `checkpoints/` 保存来源真实状态；15个子任务共享12个切点。来源关系、
事件前后边界和任务规格在 `maize_scenario_catalog.py` 中显式定义。

## 检查点重建与验收

```bash
uv run --extra wofost python scripts/build_maize_scenario_artifacts.py
```

该离线脚本重新运行三个 Python L3 Oracle，按语义事件边界保存检查点，并使用
等天气、等耗时的水肥消融对照生成固定验收门槛。`--output-root <目录>` 可在独立
目录重建以核对可复现性。`scenario_artifacts.json` 记录文件校验和、来源配置指纹、
来源验证结果和水肥对照结果；它不包含 Oracle 操作序列。

检查点包含农田、原生模型历史、待兑现投入、未来天气配置与随机状态，并额外保存
拖拉机的种子身份、原始精度燃油及粮箱、挂具、整地记录和作业日志，以及其他设备
和观测随机状态。原生 PCSE 恢复通过重放已保存历史重建模型；这与重新执行来源
L3 或计算未来状态不同。场景构建和仅捕获工作流不会执行来源 Oracle。

文件缺失、校验和不符或来源配置变化时明确报错并提示重建，不静默生成替代初态。
L1/L2 初始时间严格等于来源检查点时间。任务提示不暴露内部生理验收阈值或未来结果。

验收先审计全季资源账本，再检查任务相对初态的进展。未播种阶段的基肥、待兑现
水肥和已吸收投入分别计账；粮食守恒覆盖粮箱、接粮区和仓库，避免把收获L1错误地
要求为全季入库。所有子任务要求操作后的复查，空操作和缺失关键步骤不能通过。

水分L2采用累计水分胁迫天数，营养L2采用原生总氮吸收量，门槛是相同天气和耗时下
参考管理与移除对应操作两组结果的中点。短期营养响应不要求生物量增加5%。这些
只是固定合成场景的内部完成标准，不是新增评分体系或田间农艺标准。

## 与大豆一致的编写方式

`fairy/scenarios/maize/` 每个场景有独立 Python 模块并显式注册。
公共参数和流程组织方式沿用大豆 V2：`init_and_populate_apps()` 初始化
世界，`build_events_flow()` 用 `EventRegisterer.capture_mode()`、
`.oracle()` 和 `.depends_on()` 构建有语义名称的事件。

Oracle 的步骤在 Python 中编写，固定管理窗口是针对场景天气验证的参考路径。
场景构建与仅捕获工作流不会执行全季模拟。它不是运行时自适应策略：
更改天气或品种以后，需要重新验证操作窗口。

普通运行轨迹、回归报告和原生模型检查点仍可使用 JSON；这些文件不构成
另一套必需的 Oracle 定义。共享农田检查点保存玉米身份、行数和后端状态；
旧检查点缺少作物字段时保留大豆默认值。

## 作物参数与单位

- 原生模型：PCSE 6.0.x / `Wofost81_NWLP_CWB_CNB`。
- 玉米品种：`Grain_maize_201`；工具中的种子标识：`MAIZE_201`。
- 参数来源：上游提交
  [`1ca91d7dbb5aaf6b41462162de03a8254812d3a5`](https://github.com/ajwdewit/WOFOST_crop_parameters/blob/1ca91d7dbb5aaf6b41462162de03a8254812d3a5/maize.yaml)。
  `fairy/physics/data/wofost/maize.yaml` 原样收录，来源及校验和保存在
  `maize.provenance.json`，运行时不联网下载。
- 该参数集提供玉米 C4 光合、根系、器官分配和氮素参数，`NFIX_FR=0`。
  它是欧洲参考品种，不是已标定的中国商业品种。
- 64 垄，每垄长 268 米、宽 0.75 米、单行；株距 20 厘米对应每垄
  1,340 粒种子、约 6.67 株/平方米。库存和密度采用同一公式。
- 密度仅通过初始生物量 TDWI 缩放进入原生模型；不表示精细行间竞争模型。
- 玉米阶段使用播后未出苗、营养生长、生殖生长和成熟等粗阶段。
  成熟以原生模型成熟日期为准，不用大豆 R8 或虚构的玉米叶龄判断。

玉米首版的工程配置集中在 `fairy/physics/crop_profiles.py`：
收获水分上限 25%，干燥目标和入库上限 14%。生理成熟不等于已经适宜收获。
相关依据可参阅 [Purdue 的玉米成熟说明](https://ag.purdue.edu/news/department/agry/kernel-news/2026/04/indiana-corn-update-issue-28.html)
和 [UMN 的粮食干燥储存资料](https://blog-crop-news.extension.umn.edu/2024/03/proper-spring-grain-drying-and-storage.html)。
这些阈值是本场景约定，不作为所有地区的统一标准或最优管理建议。

原生 `TWSO` 是干物质；农田库存和回收量沿用已有系统的商品水分质量口径，
玉米固定为 14%。该质量乘以 `0.86` 得到对应干物质；物理湿重还需要结合
当前水分计算。干燥改变物理含水率，不应重复扣减已经标准化的商品质量。
玉米不报告大豆蒲式耳换算值。

## 验证与边界

本次三级扩展完成后的全仓库回归为 **552项测试通过**。18个玉米场景均覆盖独立
Oracle和确定性回放；所有15个子任务均包含空操作及缺失关键操作的失败用例。
检查点恢复覆盖装种、待兑现施肥、粮箱、湿粮和安全干粮，并验证继续来源季剩余
操作后的状态与连续运行一致。12个检查点及验收清单在独立进程重建后完全一致。

L1烘干、L2水分管理及L3正常季还通过了现有CLI的构建、回放、评估；脚本化Agent
验证了子任务终点提示和真实工具schema。两个代表性大豆Oracle与引入玉米前的
完整物理状态相同，水稻注册、检查点和回放回归通过。本次未调用远程模型。
当前验证汇总在 `validation_runs/maize_tiers_20261024/summary.json`，全量日志在
同目录 `pytest.log`，该目录按仓库规则不提交。

引入分层之前，2026-10-24 在 PCSE 6.0.13 下的首版验证有468项测试通过；三个场景经
主 CLI 捕获、回放并评估，严格验证均通过，64 垄全部成熟、收获和安全入库，
工具错误为零。下表已按多农场整合后的实际几何、作业耗时及显式200kg底肥重新执行更新。
这些数值是合成环境的软件验证结果，不能用作田间产量预测。

| 场景 | 工具调用数 | 14% 水分入库质量（kg） | 灌溉（全田等效 mm） | 肥料产品（kg） |
| --- | ---: | ---: | ---: | ---: |
| 正常（调整收获窗口后） | 191 | 2930.72 | 0 | 440 |
| 缺水 | 246 | 3221.60 | 150 | 440 |
| 缺氮 | 235 | 2898.24 | 0 | 360 |

各场景天气和管理不同，表格不是单一因素的产量排序实验。匹配天气和操作时间的
消融测试另行验证：缺水场景移除灌溉后产量为零；缺氮场景移除追肥后，
原生干物质产量从 1997.44 降至 1745.31 kg/ha。两个代表性大豆场景分别使用
旧后端和 WOFOST，与引入玉米前的农田、库存和完整物理状态逐项一致。

本地运行报告和汇总在 `validation_runs/maize_implementation_20261024/`，该目录
按现有规则被 Git 忽略。复现测试使用：

```bash
OPENAI_API_KEY=unit-test-placeholder .venv/bin/python -m pytest -q --disable-warnings
```

占位 key 仅供已有测试中的模拟客户端初始化；本次没有调用真实远程模型。

玉米测试覆盖原生 PCSE 对照、同一天水肥入账、种子与密度、成熟和水分门槛、
库存及干物质守恒、阶段显示、检查点恢复、工具 schema、Agent 作物提示词、
完整 Oracle 和回放。缺水与缺氮场景通过移除灌溉或追肥进行对照，
而不是把正常种植与完全不操作比较。

玉米沿用已有运行报告和作物来源指纹。任何产量基准必须使用相同场景、
作物参数及配置；大豆基准不兼容。未建立跨作物统一评分或本地田间产量精度结论。

首版关闭旧大豆病虫草害动态及其对玉米生长的耦合，也关闭大豆落荚损失。
专属植保、精细授粉和穗粒数、多品种、轮作仍不在当前范围内。
合成天气和未本地标定的品种用于验证工具与决策闭环，不能据此声称东北春玉米
的成熟期、产量或肥水最优策略已得到验证。
