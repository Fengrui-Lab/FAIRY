# 两配对共同公开执行器合同 v1（阶段2待实现）

## 操作边界

所有处理共享同一份执行器及版本哈希，不复制不同回执逻辑。策略函数只提出依据公开观察作出的意图；执行器负责真实公开工具调用、参数记录、回执归档、等待、去重和公开复查。此处只定义接口，不实现新的生产工具/生理模型，不运行后台“纠错”策略。

## 状态机

- `proposed -> dispatched -> accepted/pending/rejected/partial/unknown -> reconciled`。每次保存任务/环境/操作ID、垄范围、观测时间、公开参数、发出/完成时间、原始回执与native生效日期。
- 成功不只看顶层status：对照工具schema、实际数量、库存与日志；装料后的料仓增加不是施肥生效。非空error不是自动所有输入0；先确认是否原子拒绝。`ok=true,error=null`不得误报失败。
- `pending/effect_ready_at`：同垄同操作未核实原生日结算前不能重复发；等待到公开生效时点再复查。不得在backend私有状态里偷读“已恢复”；仅离线证据可查原生日输入。
- `rejected`且已证实无投入：接受量0，保留原因，返回策略决定下一步，不能自动换大剂量或不断尝试。
- `partial/unknown`：冻结该垄重复投放，用公开库存、设备、日志、回执核对；不得超时直接记0再重发。无法确定就终止该轨迹为不确定，保留其他完成证据。
- 输入去重使用同一初态/任务下的dispatch ID和垄范围，不把跨日同量合法再次灌水误删。操作日志中的随机mission/op ID不用于代替田块、日期、数量身份。

## 公平观察与时间

共同3日历天观察网格，读取根区、overview、当前天气。建植、原生日生效和临近成熟的公开复查允许增加，但两组同规则；不依据内部DVS选检查日。观察噪声种子/工具调用顺序存档；有处理引起的真实状态差时不通过事后重置RNG造一致。

把工序耗时与天气绑定记录；预设日历检查点等待到目标时间，不以“每次操作结束后再等3天”使不同处理无限漂移。对照人工灌溉造成的时间开销不伪造为空操作；不补水组按公共时间推进到相同检查时间。记录两组实际播种日、原生日和天气序列，若不同须解释或判为混杂，不能宣称完全同日输入。

## 资源与结算

- N60/N120显式load_fertilizer与base_fertilize(total_kg)，均全季仅一次基施；所有原生累计输入和料仓/库存核对，不偷补施肥。
- 水阈值0.18为冻结的开发策略阈值，不是修改工具stop阈值0.30或生理参数。按公开探头覆盖区连续垄发起20mm/垄（4小时）的操作；剩余场等效额度不足时减少最后剂量，按垄数权重精确裁剪，不超150mm。
- 毛水/有效水/原生日分别记录；20mm×0.92=18.4mm是native有效水，不等于最终根区储水；已拒绝原子动作实际水0。
- 闭环必须靠公开成熟、合法收获、卸粮、真实干燥和严格入库，不设置作物成熟或仓库质量；最后一次日结算后才读取投入总账。
- 180天模拟季、500次农事工具、1800s墙钟为拟试点预算；执行器额外等待/复查真实消耗预算，能力分析单列，不能因“不计能力”而不计预算。到限保留失败，不自动放宽。

## 实现验收先决条件

以极小合法操作证明输入只计一次、拒绝不耗资源、待生效重复被抑制、部分结果不重复施入；再运行四条全季。不得直接修改全局生产工具以使配对通过。若原生机制确有缺口，记录并暂停受影响候选，另行评估修复，不偷偷调整底层阈值。
