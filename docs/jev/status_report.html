Background

FAIRY
Digital twin of a soybean farm (Harbin, one field of 64 ridges). An agent manages it by calling tools (tractor, drone, sensors, weather, warehouse). Levels: L1 = one skill, L2 = one episode, L3 = a full season. L3-mini = the 20 scenarios in scripts/fullseason/l3_mini_20_scenario_ids.txt; we use 19 (hn50_hn84_hn58_mixed_stress was left out). Each scenario has an oracle (expert) run used for scoring.
Jev
TypeSafe's "System One" decision model (jev-latest, version 1.14.0). It is not a language model: it receives a text description of the situation plus questions with option lists, and returns a pick, a probability per option and a confidence (0–1). Limits: 255 options per question, 64k tokens per request. Price $0.042 per million input tokens, output free, no caching.
LLM agent
gpt-6-luna through the OpenAI Responses API, reasoning effort "medium", run with FAIRY's ReAct controller (farm_baseline_react). About 99% of its input is billed as cached ($0.01 per million).
Grain loss
The main yield metric: grain not harvested and stored, compared with the oracle (FAIRY's recovered_yield_loss). 100% = nothing harvested; below 0% = more than the oracle. A season counts as finished when all 64 ridges are harvested.
Task text
The scenarios' Chinese task texts were translated to English and checked by hand against the originals. Every agent gets the same English text.

How the agents work

Hybrid (Jev + LLM), the main Jev setup

  1. Code writes a short farm snapshot (date, crop state per group of ridges, inventory, equipment, what was already done). Jev does not see the full history.
  2. Jev picks the next action from a menu: the scenario's tools plus "done".
  3. Jev picks each argument from a menu built by code from the tool's limits, numbers in the task text and the farm state (never from the oracle). Waits are offered in plain units (30 min … 14 days, or "until ready"). Questions that don't depend on each other go in one request.
  4. gpt-6-luna takes over a decision when Jev's confidence is below 0.4, when Jev repeats an action that changed nothing, or after Jev's "done" was refused twice. The LLM makes one decision per call, with a memory of its own earlier calls.

Done check

When an agent says it is finished, code checks the visible farm (for example, unharvested ridges). If work is left, the "done" is refused (at most twice per run) and the agent is told what is missing. Always on in the hybrid. For LLM agents it is the option --done-check true; the fair LLM baseline below uses it, so both sides play by the same rule.

What each column shows

  • Hybrid vs LLM alone. Same yield level and both finish nearly every season. Jev makes half of the decisions; the hybrid is about twice as fast and costs about twice as much, because the LLM's cached input is cheaper than Jev's uncached input. Its one failure (compacted_headland_stand_recovery) used up all 300 actions, with the LLM making 74% of the decisions in that run.
  • Full history instead of the snapshot. Jev's input grows with every action and hits the 64k limit before harvest in every run (after 43–114 actions). The code-built snapshot is required for full seasons.
  • REFLEX-style (arXiv 2609.26532: Jev picks the tool; when unsure, the LLM only fills in that tool's arguments and cannot change the tool). 11 runs used up all 300 actions. In the hybrid, when Jev is unsure, the LLM picks a different tool in 68% of hand-offs (914 of 1,348), most often "advance time" instead of another check. REFLEX takes that away, so the season crawls forward in short steps. When it does finish it loses the least grain (2.6% on its 8 seasons, vs 4.1% hybrid and 7.6% LLM on the same 8) at about 2.6× the cost.
  • LLM with Jev as an optional tool (ask_jev: the LLM writes a state and options, Jev answers). The LLM never called Jev in 38 runs, also when a neutral note in the system prompt explained what Jev is. These runs are effectively LLM-alone runs; their spread (up to 16 points on the same scenario between the two sets) shows how large single-run noise is.

Takeaway: Jev pays off when code puts it in charge and the LLM steps in, with full freedom, when Jev is unsure. Single runs vary a lot, so differences of a few points between settings are not reliable.

Code, logs and how to rerun

Code
github.com/Synkrasis-Labs/fairy-jev, branch jev-single-farm-hybrid-and-ablations. Built on FAIRY main (commit a7654d8), single-farm soybean only. Jev code in fairy/agents/jev/. All new behaviour is behind options, off by default.
Write-up
docs/jev/review.md (sections 12–16 for the numbers here) and docs/jev/PROGRESS.md (every step, setting and cost).
Launcher
scripts/jev_run_l3mini.py runs any setting on the 19 scenarios with the exact flags used here (checked against the original commands); --dry-run prints them.
Logs
jev_single_farm_L3mini_runs.zip (189 MB): all 121 L3-mini runs in FAIRY's standard files (every Jev request with options, probabilities and confidence; every LLM call with tokens; every tool call), one folder per setting, runs_summary.csv (one row per run), FAIRY's summary_v2 scores for every run, the oracle baselines, and a README.

Multi-farm (L4): not started

The multi-crop, multi-plot scenarios live on FAIRY branch codex/wofost-management-cultivars-oracle-audit (13 commits and about 800 files on top of main, including WOFOST crop physics, rice, maize, shared equipment and a rewrite of the farm apps). Our branch and that one both change 9 files; on our side these are small hooks of a few lines each.

Our Jev agent assumes one field: the snapshot, the ridge menus and the done check all read one list of 64 ridges. On L4, Jev would also need to choose the farm or plot, and the snapshot and done check would need to cover all of them. How much work that is will be clear after running one two-farm scenario with the LLM agent on that branch.

Limits of these results

  • One run per scenario on L3-mini; single runs vary a lot.
  • One LLM (gpt-6-luna) and one Jev version (1.14.0).
  • Jev's results depend on how its menus and snapshot are built; that design was refined during development on a few L1–L3 scenarios.
  • Cost compares dollars at current prices; the LLM's advantage comes from cached input, which Jev does not offer.
