## 2. 本轮唯一的已有物理源码修改：显式外来水

文件：[wofost_backend.py](/Users/quao/.codex/worktrees/wofost-management-audit/FAIRY/fairy/physics/wofost_backend.py)。

原贫排水场景在 44–53 垄设置 `rainfall_capture_efficiency=1.02`。把它直接映射为原生 `NOTINF=1-1.02=-0.02` 会把额外水伪装成本地降雨；裁剪到 1 又会静默丢失场景原来的额外来水假设。上轮版本选择拒绝这种转换。本轮保留默认拒绝，增加有明确来源说明的可选外部水输入。

| 改动 | 为什么需要 | 实际约束 |
|---|---|---|
| `allow_external_runon=False`、`external_runon_source` | 将额外来水变成显式场景选择，避免所有场景默认放宽 | 必须是真正布尔值；启用必须提供非空来源；单独给来源也拒绝 |
| `_external_runon_declaration()` | 在构造任一垄原生模型之前检查边界水假设 | 超过 1 的捕获系数必须显式授权；与非零 `NOTINF` override 冲突时拒绝 |
| 分离本地降雨和来水 | 保持原天气 `RAIN` 不变 | 受影响垄 `NOTINF=0`，来水为 `(capture-1)×当日本地雨量` |
| 合并一次原生灌水信号 | PCSE CWB 的灌水回调会替换待用值，连续发两个信号会覆盖一个来源 | 原生信号为“实际管理灌水×灌水效率 + 外来水”，信号效率设为 1；来源仍分别记账 |
| 原生日输入来源、比例校验 | 回放和检查点不能额外制造没有来源或比例不符的水 | 每日 journal 的来水量、来源必须与声明及原天气一致 |
| 单独累计两种水 | 原生 `TOTIRR` 此时含外来水，不能全部算作 Agent 灌水 | 保留工具实际毛灌水；新增有效管理灌水和外来水累计，以及 `TOTIRR` 差额 |
| 播前来水记录 | 播前辅助土壤已经吸收来水，初始 `SM/WAV` 已包含它 | 记录进来源账；播种时不再次发送同一笔原生灌水 |
| snapshot/checkpoint 字段 | 后续恢复及重放需要保持来源和累计账一致 | 保存播前来水、逐日日志及累计量，恢复无权限的来水检查点时拒绝 |

只有 `scenario_full_season_hb_poordrainage_wetjune_disease_trafficability` 的显式运行变体启用它。2% 来水是对原场景经验系数的来源标记和守恒拆分；没有上游面积、径流系数或实测径流资料，**不是经过标定的集水区水文模型**。外来水不扣 Agent 灌溉额度，不改天气，也不计成工具灌水。

## 4. 新增逐场驱动：配对反事实及有限候选选择

文件：[calibrate_formal90_oracles.py](/Users/quao/.codex/worktrees/wofost-management-audit/FAIRY/scripts/calibrate_formal90_oracles.py)。

1. 为每个正式 ID 保留原始 workflow、逐场审查、实际 WOFOST 配置、初始状态和 508 文件指纹，公开观测编译出的参考流程从新场景重放。
2. 把一次管理决定的多个连续喷杆或人工作业组成 episode，逐个做删除、半剂量及适用的模拟参考工作液剂量试验。删除动作以真实读时 no-op 占位，保持其余动作绝对时刻；半量肥试验保持载水量不变。删除水肥整次动作同时删除肥和载水，不能单独归因为氮。
3. 每个候选从相同初态重放。独立可删除不等于联合可删除，所以多 episode 删除与各 episode 最佳选择的组合另跑联合对照。
4. 只允许所有垄成熟、收割、安全入库且无工具失败的候选进入选择；目标是安全入库质量。在最高候选的 0.1 kg 容差内，依次优先更少管理次数、工作液、肥料及灌水。高产但未完成的候选不能获胜。
5. 选中方案再从新场景执行一次，对比原生导出状态以及每步工具名、参数、响应和绝对时刻。保存完整可执行 workflow，提供 `--replay-case` 入口；源码指纹不同就拒绝宣称精确复现。
6. 密度候选独立运行同一公开自适应策略，原规定密度仍保留。该比较不是固定绝对时刻的纯密度消融，也不因 TDWI 随密度线性变化就宣称找到农艺最优密度。

这里的结论是“本轮实际测试过的有限候选中较好的方案”。没有连续日期、全部药量、所有组合的全局搜索，不宣称最高理论产量或田间最优。剂量单位是工具实际产品质量或工作液，不是现实农药有效成分推荐量。

### 主批冻结之后独立补充：原灌水量是否偏少

文件：[extend_formal90_water_search.py](/Users/quao/.codex/worktrees/wofost-management-audit/FAIRY/scripts/extend_formal90_water_search.py)。主批的删/半量试验不能检验原灌水量是否偏少，因此新增独立扩展；它不改原有 508 文件、主批 `selected/` 或主批 `summary.json`。

每个参考 `FieldOpsApp__irrigate` episode 使用**原 observed reference 的小时数×2**，其余动作采用主批已经选定的方案。主批若删掉或减半灌水，仍恢复原参考灌水工具及范围再翻倍，不拿主批半量翻倍冒充新的高水候选。原始库存、配置、逐场审查、配额与场景期限保持一致。

加长泵时是真实作业，不能把原结束时间强写回去。扩展逐步手动调用注册工具，记录真实 `time_before/time_after`，超过原槽的耗时累计顺延所有后续槽；较短操作仍用真实等待保留原槽。原步骤 ID 和非水动作参数全部保留，只增加必要的 System 等待。遇到真实错误、部分覆盖、灌水仍 pending、配额不足、超过原期限或未能成熟安全入库，候选记为不可行，不补库存、不增加配额，也不新增自适应侦察或天气重规划。

合法执行的完整记录再从新场景 `Engine.replay_workflow()` 回放，核对初态、终态及清理随机回执 ID 后的全部工具参数、响应和时刻。只有真实完成、鲜回放一致且安全入库比主批提高**超过 0.1 kg**的候选可替换主批。多个独立高水 episode 都有效时，组合还要单独实跑；不能把独立收益直接相加。资源约束仅指当前代码实际实现的库存、配额和设备约束，没有把分次灌水代理说成新增了原生电力模型。

这是一组“水量与实际作业时刻共同变化”的合法计划比较，不是固定时刻的纯水量效应。候选、完整工作流、四份初终态快照、实际顺延表和选择理由单独保存在各场 `supplemental_water_search/`。扩展脚本自身 SHA 与原 508 字典指纹分别核验；最终方案的独立复现入口为：

```bash
env -u USER PYTHONHASHSEED=0 .venv/bin/python scripts/extend_formal90_water_search.py \
  --replay-case <正式结果中的case目录> --output-dir <新的复现输出目录>
```

`--output-root <final_v1目录> --workers 2 --watch` 在主批运行中只处理已完成案例，最多启动两个额外工作进程。它检查全部 90 个 ID，原生补种阻塞仍沿用主批结论，不生成伪造的高水成功。

复现命令必须保留 `PYTHONHASHSEED=0`，与主批和扩展工作进程一致：原有无人机使用 Python 内建 hash 派生观测 RNG。未设置时，实际产量仍可能相同，但 RNG 初态和观测回执不同，不能宣称初态/全轨迹精确复现。这项环境要求不通过删去 RNG 字段或放宽快照比较来规避。
