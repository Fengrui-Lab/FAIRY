# 工具接口重构：官方框架依据与实现边界

核实日期：2026-10-23。

本文件记录已阅读的官方资料、从中作出的 FAIRY 设计决策，以及需要用代码和测试证明的要求。它不是功能完成清单，不以“参考了某框架”代替本项目的实现证据。

研究范围是工具定义、参数说明、运行时上下文、调用一致性。农场物理模型、共享设备的物料账和场景 Oracle 仍是 FAIRY 自己负责的领域逻辑，不由通用 Agent 框架保证。

## 1. 从官方代码中实际看到了什么

### OpenAI Agents SDK

官方 Agent definitions 使用普通 Python 函数声明工具，再交给 Agent 的 `tools`。它同时区分模型可见的对话内容与代码本地使用的 context；模型需要的信息必须通过可见输入交付，运行时依赖可以留在本地。[官方 Agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents)

Quickstart 将工具显式交给 Agent，由 Runner 组织执行；这支持将“提供什么能力”和“如何运行一个 Agent”分别表达。[官方 Quickstart](https://developers.openai.com/api/docs/guides/agents/quickstart)

本机另外核实了 `openai-agents 0.24.0` 的 `agents/function_schema.py`：

- `FuncSchema` 同时保存原函数签名、Pydantic 参数模型和由该模型生成的 JSON Schema。
- `function_schema()` 从实际签名、类型、默认值、docstring 与 `Annotated` 元数据提取声明。
- `RunContextWrapper`／`ToolContext` 是运行时上下文；该版本要求它位于首参数，并从模型输入中排除。
- `to_call_args()` 根据保留的签名，把已验证参数转为原函数调用参数。

本地核实路径：`/private/tmp/fairy-wofost-env/lib/python3.10/site-packages/agents/function_schema.py`。版本由同目录 `openai_agents-0.24.0.dist-info/METADATA` 确认。它是研究时读取的安装副本，不是 FAIRY 的生产依赖声明，也不保证临时目录永久存在。

### Google Agent Development Kit

ADK 的 `FunctionTool` 从 callable 获取名称和说明，使用共用的 `CallableSpec` 提取签名、类型和上下文参数。生成模型声明时排除注入的 context，实际调用前再注入它。[FunctionTool 官方源码](https://github.com/google/adk-python/blob/main/src/google/adk/tools/function_tool.py)、[CallableSpec 官方源码](https://github.com/google/adk-python/blob/main/src/google/adk/utils/_callable_utils.py)

官方文档要求清楚的函数签名，参数类型、默认值和说明参与工具声明；`ToolContext` 由框架注入并对 LLM 隐藏。[函数工具及上下文文档](https://adk.dev/tools-custom/function-tools/)

ADK 内部也会生成调整过的 `__signature__`，用于从已声明函数中去掉不向模型公开的参数。因此，“用了反射或 `__signature__` 就不可靠”并不是研究结论。[声明生成官方源码](https://github.com/google/adk-python/blob/main/src/google/adk/tools/_automatic_function_calling_util.py)

### Microsoft Agent Framework

微软官方 Python 示例采用真实函数参数，使用 `Annotated` 与 Pydantic `Field` 提供参数说明；`@tool` 可以显式声明工具名称和说明。`FunctionInvocationContext` 承载每次调用的运行时数据，向模型生成 Schema 时隐藏。[函数工具官方文档](https://learn.microsoft.com/en-us/agent-framework/agents/tools/function-tools)

源码中的 `FunctionTool._resolve_input_model()` 从签名和类型创建输入模型，排除上下文参数。它也接受单独的输入模型或 JSON Schema；源码明确说明裸 Schema 字典只有有限校验，不能等同于类型化模型的递归验证。[工具实现官方源码](https://github.com/microsoft/agent-framework/blob/main/python/packages/core/agent_framework/_tools.py)

以上为阅读时的文档和主分支行为。主分支 URL 会变化；本次没有把这些框架整体引入 FAIRY，也没有据此宣称任一框架能自动验证农业描述是否真实。

## 2. 本项目采用的设计判断

共同可借鉴的做法是：业务 API 可以直接阅读；模型参数与运行时依赖分开；名称、类型、默认值和参数说明有明确来源；生成声明和执行调用之间保留可检查的对应关系。

据此，FAIRY 的共享服务应使用静态定义的普通类和真实方法。例如 `DroneService.fly_survey` 的源码就应声明 `farm_id`、`asset_id`、`start_ridge`、`end_ridge`。读者应能通过查找方法定义，看到完整调用方式。

共享服务不再依靠以下过程形成新的业务接口：

1. 扫描旧单场 App 的全部方法。
2. 在运行时添加 `farm_id`、`asset_id`。
3. 改写部分参数名称。
4. 复制旧 docstring，再拼接新场景说明。
5. 创建动态类，并设置一个比实际函数体更具体的 `__signature__`。

正常的装饰器、类型反射、Schema 编译和实例绑定仍然可以使用。需要去掉的是这些机制对业务接口的隐式改造，不是去掉通用编译基础设施。

### 公开参数与内部上下文

| 信息 | 所属位置 | 原因 |
|---|---|---|
| `farm_id` | 真实公开工具参数 | Agent 必须选择目标农场 |
| `asset_id` | 需要设备的真实公开工具参数 | Agent 必须选择哪台资产 |
| `start_ridge`／`end_ridge` | 真实公开工具参数 | Agent 必须指定该场内作业范围 |
| 农场、设备对象引用 | 类型明确的内部操作上下文 | 由运行时解析，不让模型构造 Python 对象 |
| 时钟、日志记录器、站点后端 | 构造依赖或内部操作上下文 | 是执行依赖，不是模型选择项 |
| 合法 ID、作物限制和设备能力 | 场景目录与能力查询 | 模型需要知道，但不能替代实时状态 |
| 当前电量、载荷和土壤观测 | 实际状态／观测工具结果 | 会随运行变化 |

可以从同一个参数定义生成 Schema，并由场景填入合法实体 ID 等约束。场景不应添加新参数、修改参数类型或重新命名公开参数。农场与资产的联合合法性，以及当前载荷、天气、成熟等条件，仍由运行时和领域操作检查。

### 静态服务和类型明确的操作上下文

目标结构中的每层职责应能独立说明：

| 层 | 责任 |
|---|---|
| 公开服务方法 | 声明完整参数与说明；进入统一执行入口 |
| 工具编译／注册 | 从真实公开方法构造契约，校验结构对应关系 |
| 执行器 | 验证模型参数，取得本次上下文，记录结果 |
| 农场运行时 | 按 ID 解析农场、资产、站点和公共时钟 |
| 类型明确的操作对象／上下文 | 在本次调用中访问正确的农场与唯一资产状态 |
| 农业操作实现 | 实际前置条件、耗时、资源消耗和业务结果 |
| 物理引擎 | 根据管理动作、天气和时间演化农场状态 |
| 独立场景文件 | 本次世界输入、初始化、Oracle、事件图和验收 |

设备操作应显式使用上下文中的农场与资产。新的共享路径不应继续用动态设备子类，把一个对象的 `self` 属性访问临时解释为另一套状态。旧算法可以保留并抽取复用，但新旧兼容适配的位置必须清楚，不能让公开工具依赖难以追踪的动态属性代理。

这是一组代码落地方向，是否完成须检查实际实现和验证结果。本文件不替实现作提前保证。

## 3. “Agent 拿到的说明准确”需要分层证明

从同一份定义生成 Schema 可以减少漂移，但不能自动证明自然语言和业务行为一致。

| 能用结构检查证明的内容 | 必须另外验证的内容 |
|---|---|
| 工具和参数说明是否非空 | 描述的业务含义是否真实 |
| 文档是否引用已经删除的参数 | 条件分支是否与描述一致 |
| 参数名称、类型、必填项和默认值是否对应真实签名 | 低电量时是否真的部分返航 |
| 元数据是否指向存在的参数 | 实际返回是否包含完成与遗漏范围 |
| 合法 ID 是否来自当前场景 | 是否只修改所选农场 |
| 注册名称与实际 callable 是否一一对应 | 换场后设备状态是否连续 |
| 模型收到的 Schema 是否等于注册结果 | 错误发生前后是否扣库、耗时或有部分效果 |

### 注册时应拒绝的结构问题

对于新的共享服务，验收应覆盖：

- 没有工具说明，或模型参数缺少说明。
- 参数缺少明确类型，或元数据引用不存在的参数。
- docstring 参数节仍使用已经删除的名字。
- 公开业务入口只有 `*args`／`**kwargs`，依赖另设签名掩盖真实入口。
- 声明中的参数、默认值与实际公开方法不一致。
- 工具重名，或 Schema 对应的名称找不到唯一 callable。
- 场景约束覆盖了原参数类型、名称或默认值，而非收紧合法对象集合。

读取真实函数生成声明优先于两份手写声明。如果确实采用独立输入模型，注册处必须明确这是模型驱动的接口，并检查调用适配关系；不能在形式上保留签名检查，实际却由无类型 `**kwargs` 接住所有字段。

这些严格要求针对新的共享业务接口。旧通用工具迁移需要独立兼容策略，不能无说明地改变全部历史接口行为。

### `fly_survey` 的语义验收示例

其说明需要覆盖目标农场、物理无人机、包含两端的本地垄范围，以及电量不足可能部分完成。实际测试至少应核对：

1. 把最终 Schema 交给真实 Agent 的模型调用入口，确认四个参数和说明实际送出。
2. 同一台无人机先飞 A 场再飞 B 场，观测来自正确农场，电量连续扣减。
3. 无效农场、错误资产种类、越界范围在经营操作前拒绝。
4. 低电量触发部分完成时，报告已完成和遗漏垄，且耗时与耗电符合实际结果。
5. 直接公开调用、Agent callable、事件执行和文件回放进入相同业务行为。

这些测试支持具体已覆盖行为，不等于证明所有未来参数组合正确，也不等于真实 LLM 已具备全季管理成功率。

## 4. 研究时发现的本地缺口

在改写前的代码上，最小只读复现确认了四项问题：

| 复现 | 当时结果 | 对应约束 |
|---|---|---|
| `ToolContract.from_callable()` 输入无说明函数 | 工具和参数说明可为空 | 新接口要求完整说明 |
| 真实参数是 `farm_id`，Args 只写 `old_field_id` | 旧参数说明静默丢弃 | 旧参数名应导致注册失败 |
| 变参函数手动赋 `__signature__` | 可绕过公开变参检查 | 检查真实业务声明，不能只信覆盖属性 |
| handler 仅为 `context, **kwargs` | 可以注册 | 区分真正类型化对应关系与通用适配器 |

这些是研究时的行为记录，不表示重构后的代码仍然如此。相应回归测试和实际源码应作为修复证据；本文件不通过修改措辞把缺口算作解决。

## 5. 迁移约束

本轮整理工具边界时，应保留此前多农场与多作物已经建立的业务约束：

- 共享工具服务与物理资产分别配置，同一资产只有一份油、电、载荷和日志状态。
- `farm_id`／`asset_id` 保持显式，设备自身操作不猜测一个目标农场。
- 垄号属于所选农场，几何与作物约束来自该场。
- 返还物资按实际来源处理，粮食批次归属和资源守恒不能丢失。
- 公共时间推进全部农场，不能因为更换工具封装再次推进一遍。
- 工具目录变更后，保存的 Oracle、manifest 和回放证据必须按新目录重新生成和核对。
- 八个全季场景继续各有完整配置、初始化、`build_events_flow()`、Oracle 和验收；复用集中在平台能力。
- 旧单场 App 和旧前缀工作流的兼容应有明确入口，不能让旧适配器决定新接口的公开签名。
- 快照保存和恢复必须继续保持农场、资产、站点、时钟和随机状态的独立性。

研究结论支撑的是更清楚的代码组织与契约来源。最终是否达到要求，应以实际工具声明、模型收到的 Schema、领域行为测试和场景回放记录共同判断。
