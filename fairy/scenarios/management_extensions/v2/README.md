# 新经营场景：连续跨年与多目标运营

本目录新增两个独立场景家族，旧 management_extensions 四场景及其工具、天气、Oracle、评分保持原样。

- `l3/`：同一季的不同地块、多作物经营。联合目标按各作物收入与真实投入成本计算，不把不同作物公斤数相加作为联合产量。
- `l4/`：真实跨年的原生作物生命周期。跨年不是加载一个重置了土壤、库存和设备的新场景。

两条线均在当前模拟环境搜索参考策略，不预填产量门槛，不沿用旧场景的 99% 门槛。每条线的 README、reference.json、候选记录和独立回放报告共同给出可核验的搜索范围与结果。

## 目标与最优性

农业与运营约束在搜索前确定；价格、天气、土壤、面积及品种不能为了让选定策略胜出而调节。
每个候选都通过公开工具执行，保留失败原因、实际投入、粮食来源、模拟时间和工具轨迹。
分别记录每作物产量、收入、成本、净收益和资源消耗，记录可行集合及 Pareto 非支配方案。
最高测试产量、最高净收益及最低投入方案可能不同；分别保存，不强迫一个 Oracle 同时最大化冲突目标。

有限候选全枚举只能声称该集合内最优。连续管理搜索只能声称最佳已知可行解，需公开边界、搜索维度和未搜索维度。
不把未经校准的 WOFOST 模拟收益称为真实农场保证；环境核算必须注明是原生过程量还是独立的核算指标。
若固定天气下离线优化使用全季天气，应注明为事后参考，不能宣称其信息条件等同于只见短期预报的 Agent。

## 隔离和框架接口

新增工具和状态由新场景实例显式装配。不 monkey patch，不更改旧工具签名、公共配置或共享默认对象。
场景仍使用原框架 Scenario、公开 App 工具、EventRegisterer、Engine 和 Workflow。
校准代码离线运行，不在场景 setup/build_events_flow 中优化；发布的参考工作流须在新初态中独立回放。
暂未取得完整回放和目标证据的原型不得作为已校准正式场景宣传。

状态中新增的业务字段必须参与保存和恢复。L4 季间土壤逐日结算，天气连续，时钟单调，仓库和设备延续；开始下一季只开启新作物生命周期。
输入、面积、单位、成本与粮食水分口径必须公开。实际消耗与库存转移分别记账，不能把装料、卸料当成施用或收入。

## 验证要求

1. 场景构图无农业动作副作用；生成可审查的公开工具轨迹。
2. 候选边界、可行性、目标值可从记录重新计算。
3. 选定参考独立 replay，核对目标、资源与时间；失败和补救事件不可跳过。
4. L4 验证跨年土壤连续、季间逐日结算、第二季状态恢复与物资守恒。
5. 无操作、违反资源约束、遗漏收获/入库等反例不能通过。
6. 新模块导入和注册后，旧场景构图、工具与代表性回放回归通过；旧源码改动应仅限明确的新增场景注册入口。

## 已验证的 L3 运营场景

场景 ID：`scenario_l3_joint_maize_soybean_operating_margin`。两个地块共同使用拖拉机、仓库、时钟和900m³水源；玉米面积3216m²、大豆面积4716.8m²。原有单场景和公共引擎不作修改。

搜索122个不同候选，83个可行，39个因共享水量上限被拒绝。两条起点路线均检查完整的相邻剂量组合及中心剂量的灌水时间替代，达到声明邻域内无收益改善。参考为玉米450kg/ha肥料产品、165mm水，大豆75mm水；这是有限搜索内最佳已知经营方案。

| 指标 | 参考结果 |
| --- | ---: |
| 玉米安全入库 | 4184.44kg |
| 大豆安全入库 | 1960.04kg |
| 存粮价值 | 1928.128 DEMO |
| 实际投入成本 | 642.608364 DEMO |
| 净经营收益 | 1285.519636 DEMO |
| 共享水量消耗 | 884.4m³ |
| 静态工作流 | 160步 |

最高测试存粮价值方案的净收益为1279.408436 DEMO，低于经营参考，显示产出和投入存在实际权衡。价格为搜索前固定的合成条件，不代表市场报价。任务完成与经营质量分别评测，未施加预填产量门槛；未把两种作物公斤数相加做目标。

详细搜索范围、未搜索维度、参考指纹及复现步骤见 `l3/README.txt`、`l3/reference.json`。搜索是固定已知环境下的离线事后基准，不代表与只见短期天气预报的Agent具有同等信息。

使用原框架入口（在仓库根目录）：

```sh
PYTHONPATH=. .venv/bin/python -m fairy.cli \
  --scenario scenario_l3_joint_maize_soybean_operating_margin \
  --build-oracle --replay --evaluate \
  --output-dir validation_runs/l3_joint/cli
```

读取运行报告的 `evaluation.validation.metadata`：含分作物存粮、各项成本、净收益、可行性及有符号 `margin_regret`。这个多作物经济场景不套用单作物公斤产量的通用YieldLoss。

## L4 跨季决策的实测对照

首版范围是同田玉米两年（2026、2027），不是跨物种轮作。原生土壤在休耕期继续结算；第二次播种沿用同一原生模型和土壤实例。季别粮账只计本季新增安全库存。

正式搜索中的以下对照使用相同的第一季400kg、第二季800kg肥料产品，改变第一季灌水分配上限：

| 指标 | 第一季水上限200mm | 第一季水上限300mm |
| --- | ---: | ---: |
| 第一季实际灌水 | 150mm | 225mm |
| 第一季安全入库 | 14308.80kg | 14308.80kg |
| 第二季实际灌水 | 125mm | 131.25mm |
| 第二季安全入库 | 15083.84kg | 13968.96kg |
| 两季累计安全入库 | 29392.64kg | 28277.76kg |

第二季较好方案在7月4日、14日各灌62.5mm；另一个方案同期各灌43.75mm，并在7月24日再灌43.75mm。因此这是跨季配额、单次剂量、土壤状态和观测触发时机的联合效果，不能单因解释成“第二季总水量更少”。候选原始记录为 `validation_runs/management_v2_development_20261102/l4/search/f400_w200.json` 和 `f400_w300.json`。

累计产量与有符号YieldLoss由本场 `evaluation.validation.metadata` 提供，按两季安全入库账计算。通用单季FOS读取末季田间状态，不能代替本场累计指标。天气为固定合成气候，模型未增加冻土与积雪过程，当前结果是模拟环境内的参考，不是地区农艺生产保证。

## L4 搜索结果与正式运行入口

场景 ID：`scenario_l4_two_year_maize_soil_carryover`。19个候选均可行；最终最佳第一季肥料产品500kg、灌水上限150mm，第二季肥料700kg、灌水额度从全程400mm中扣除第一季实耗后结转，仍受单季300mm上限约束。

| 指标 | 2026季 | 2027季 | 两季累计 |
| --- | ---: | ---: | ---: |
| 安全入库量 | 14727.04kg | 14888.00kg | 29615.04kg |
| 实施肥料产品 | 500kg | 700kg | 1200kg |
| 实际全田等效灌水 | 150mm | 125mm | 275mm |

静态Oracle为263步，包含任务说明、观察、作业和时间推进。先完成3×3粗网格，再按100kg肥料产品、50mm水量的完整二维相邻组合细化；最终最佳点的8个相邻组合均未改善产量。播期、品种、密度和管理窗口固定，不能声称任意农业管理空间中的全局最优。

```sh
PYTHONPATH=. .venv/bin/python -m fairy.cli \
  --scenario scenario_l4_two_year_maize_soil_carryover \
  --build-oracle --replay --evaluate \
  --output-dir validation_runs/l4_two_year/cli
```

本场显式固定观测随机种子，普通CLI不依赖进程级 `PYTHONHASHSEED`。原始9点粗网格未内嵌运行时输入指纹，reference诚实记录这一证据限制；后10个邻域点（含最终选中点）有原始输入指纹，全部19个候选有文件哈希，最终Oracle已经以独立执行和回放结果核对。完整搜索、发布与验证命令见 `l4/README.md`。

## 最终验证与旧场景隔离

- 两个场景均通过原 `fairy.cli --build-oracle --replay --evaluate` 入口；使用不同进程哈希时仍复现参考指标。
- 两条静态Oracle都通过纯捕获、真实执行、保存JSON后全新实例回放；状态比较排除随机操作ID并把浮点规范到9位。
- 注册后80项旧入口/历史错误回放/天气描述与新增场景测试全部通过。
- 原有4个management_extensions场景的完整Oracle执行与全新实例回放全部通过。
- 起始1550个已跟踪文件中，仅显式场景注册列表变化；旧场景、公共工具和引擎源码不变。

可核验证据位于 `validation_runs/management_v2_development_20261102/`：L3最新独立报告为 `l3/verification_drying_ledger/verification.json`，L4为 `l4/verified/verification.json`；各家族的 `parent_candidate_audit.json` 保存独立候选复核结果。运行报告中的 `evaluation.validation.metadata` 给出对应家族指标。两套真实basic/detail任务文本分别保存在 `l3/task_descriptions.json`、`l4/task_descriptions.json`。
